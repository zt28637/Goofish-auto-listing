# 优化路线图 — Agent 四轴

> **用途**：把「这套 RPA 能跑」推进到「这套 Agent 系统可交付」。
> **与《失败模式清单》的分工**：那份回答「它会在什么条件下坏」；这份回答「接下来往哪推、按什么顺序、怎么算做到了」。
> **收录口径**：每条优化点必须带**本仓真实证据**（故障、人工救火、手工核对），不接受假设性优化。没有证据的条目一律进不了 P0。

## 图例

| 标记 | 含义 |
|---|---|
| **P0** | 今天已真实发生过损失，不做就是等它再发生一次 |
| **P1** | 让 P0 的成果可验证、可回归 |
| **P2** | 决定这个项目是「技术案例」还是「商业案例」 |
| 🟢 / 🟡 / 🔴 | 已覆盖 / 部分覆盖 / 未覆盖 |

> 编号前缀：**D** 开发流程 · **O** 运行维护 · **Q** 数据质量 · **B** 业务决策。

---

## 定位：四条轴各证明什么

| 轴 | 回答的问题 | 做完证明什么 | 现状 |
|---|---|---|---|
| **D 开发流程** | 改得对不对 | 你能驾驭 Agent 做**有风险的改动**，而不是只会让它从零生成 | 🟡 有能力无机制 |
| **O 运行维护** | 跑得稳不稳 | 你把它当**生产系统**，不是一次性脚本 | 🔴 靠人工兜底 |
| **Q 数据质量** | 输入靠不靠谱 | 你知道坏数据比坏代码更贵 | 🔴 预检放过真错误 |
| **B 业务决策** | 值不值得跑 | 你不只是执行者，还是**经营者** | ⚪ 几乎空白 |

> 前三条做完 = 可靠的工具作者；第四条做完 = 经营者。**前三条都能用 11-07 的故障当论据，第四条只能靠真实销售数据长出来。**

## 一、Agent 开发流程（D）

**现状**：人给目标 → Agent 经 MCP 改画布 → `app.save` 编译 → 跑一次看结果。改动无版本、无回归、无独立审查。

| 编号 | 现状缺口 | 证据（2026-11-07） | 改法 | 衡量指标 | 优先级 |
|---|---|---|---|---|---|
| D1 | 画布改动不可回放：转录只出 `.md`，拿不到结构化 diff | 回滚旧表达式只能靠对话记忆 | MCP 改动前后各导出一次 `blocks.json` 入 git | 任意改动 1 分钟内可 diff / `git revert` | **P0** |
| D2 | 只有「编译过了」这一道闸 | 157→176→185 三次块数变更全靠人工核对 | 改完自动三关：编译 → 静态检查 → 转录 diff（块数/指令类型分布），异常即拦 | 三关全过才允许 `app.run` | **P0** |
| D3 | 文字约束无法验证 | 分类级联无出口守卫，直到死循环才被发现 | 把 AGENTS.md 约束变静态断言：「每个 Excel 写块必配保存块」「每个 While 必有出口/守卫」 | 断言覆盖今日 3 类故障中的 ≥2 类 | **P1** |
| D4 | 单 Agent 自审不可靠 | 当日 Agent 3 处错误（J9 写反、作用域破坏、`datetime.replace` 误判）**全部由人现场抓出** | 写作 Agent 与审查 Agent 分离，红队视角复核 | 独立审查发现的问题数 / 漏到运行期的问题数 | P1 |
| D5 | 推理不留痕 | 「为什么加 Try/Catch」「为什么换 xpath」只存在于对话里 | 每次画布改动附 `docs/adr/NNN-*.md`，三句话：背景/选择/代价 | 每次 P0 级改动都有对应 ADR | P2 |

## 二、Agent 运行维护（O）

**现状**：人工触发、失败靠人翻日志、无调度无告警；进程与文件锁残留会直接毁掉下一轮。

| 编号 | 现状缺口 | 证据（2026-11-07） | 改法 | 衡量指标 | 优先级 |
|---|---|---|---|---|---|
| O1 | 无前置健康检查 | 10:31 WPS 占用 `商品清单.xlsx`，写表 `PermissionError`，需人工手动关 WPS 才能继续 | 启动检查：`~$` 锁文件、WPS/Excel 残留进程、浏览器实例数、登录态有效期、磁盘 | 5 项检查全过才启动；已知故障可被自动识别 | **P0** |
| O2 | 残留状态靠人工对账 | AGENTS 明文要求「残留『上架中』须先对账」——当日正是人工完成 | 启动时扫 N 列「上架中」→ 对照闲鱼实际 → 自动改回「待上架」或「上架成功」 | 崩溃后重跑无需人工改表 | **P0** |
| O3 | 日志是自由文本 | `logs/*.txt` 只能人眼读，无法统计 | 改 JSONL：`{run_id, 行号, 阶段, 耗时, 结果, 失败码}` | 能算出分阶段耗时、失败原因分布、单件 P50/P95 | P1 |
| O4 | **无重复发布防护** | 10:25 测试轮把 P001 又发了一次，需人工去闲鱼下架 | 发布前查重：标题+首图 hash，或维护已发布台账 | 重复发布次数 = 0 | **P0** |
| O5 | 失败无人知晓 | 三项计数只打印/导出，要等下次打开 Studio 才看见 | 失败 / 登录失效 / 整轮超时 → 企业微信或邮件 | 异常 5 分钟内触达 | P1 |
| O6 | 无节流 | 5 件连续发布，单件间隔数秒 | 单件间隔 + 每小时上限，配置化 | 可配置节流参数 | P1 |
| O7 | 资源不回收 | 曾观察到多个 `ShadowBotBrowser` 残留进程 | 收尾（含失败路径）强制清理 | 运行结束后无残留进程 | P2 |

## 三、Agent 数据质量（Q）

**现状**：`precheck` 只查四项必填（分类非空、价格 > 0、套图目录存在、描述非空且 ≤1500）。

| 编号 | 现状缺口 | 证据（2026-11-07） | 改法 | 衡量指标 | 优先级 |
|---|---|---|---|---|---|
| Q1 | **预检拦不住分类错误** | P002 段序错位（「全新」插在第 4 位），预检照样给 `pass=5`，执行层死循环 | 建「品类 → 级联字段顺序」参考表，校验段序与段数 | 能复现拦住 P002 类错误（pass → fail） | **P0** |
| Q2 | 预检与执行两套口径 | 预检 PASS ≠ 执行能过，当日连续两次在预检通过后失败 | 执行层失败码回流，同一套规则演进 | 预检漏放率（预检 PASS 但执行失败的比例）下降 | P1 |
| Q3 | 值域校验过粗 | 只判非空与 `>0`；原价空、发货空会静默落 `else` 走「无需邮寄」 | 价格区间（防 199/1990 级错位）、描述违禁词与联系方式、图片尺寸/数量/重复 | 静默错发 = 0 | P1 |
| Q4 | 三处块数靠手工对齐 | 157→176→185，每次都要手改 README / AGENTS / 转录 | 脚本比对：画布实际块数 vs 转录 `.md` vs 文档声称值 | 不一致自动报错，无需人工记忆 | P1 |
| Q5 | Excel 变更不可审计 | 文件直接覆盖，改了哪列、哪次运行改的，无法追溯 | 每轮运行前快照 + 收尾 diff | 任一轮可回答「谁改了哪格」 | P2 |
| Q6 | 失败原因列全靠人工 | 判定只回写 N 列状态，失败原因列(14) 空白 | 失败码自动写入（如 `CAT_NOT_FOUND:L4`） | 失败样本可直接聚合分析 | P1 |

## 四、Agent 业务决策（B）

**现状**：Agent **只执行，不决策**。上不上、什么时候上、多少钱，全部由人。四条轴里最空的一条。

| 编号 | 现状缺口 | 证据（2026-11-07） | 改法 | 衡量指标 | 优先级 |
|---|---|---|---|---|---|
| B1 | 按 Excel 行序无脑全跑 | 5 行顺序执行，不区分价值 | 按利润率 / 库存 / 竞争度排序，决定本轮发哪几件 | 单轮产出价值可量化 | P2 |
| B2 | 无择时 | 10:50 连续发 4 件（注意：O6 是技术节流，本条是业务择时） | 按流量高峰（闲鱼晚间）排期，分散到多天 | 发布时段分布可控 | P2 |
| B3 | 定价完全人工 | 价格直接取自 Excel | 参考同款在售价、原价折扣锚点 | 定价偏差 ≤ 阈值 | P2 |
| B4 | 失败后无策略 | 已有「成功/失败/不明」三分类，但没有重试预算 | 哪些可自动重试、重试几次、超限转人工 | 自动恢复率 / 人工介入率 | P1 |
| B5 | **效果闭环断裂** | 终点是「上架成功」，与「卖得掉」之间没有连线 | 上架 N 天无浏览 → 调价 / 重发 / 下架 | 能回答「这批货卖得动吗」 | P2 |
| B6 | 无风控决策 | 同类目集中、短时高频，账号风险未知 | 设定类目/账号批量上限与描述红线 | 无风控告警 | P1 |

## 五、推进顺序

| 批次 | 条目 | 为什么是它 | 依赖 |
|---|---|---|---|
| **第 1 批（止血）** | Q1 分类顺序校验 · O1 健康检查 · O4 重复发布防护 · D1 画布版本化 · D2 三关闸 | 全是 11-07 **真实造成损失**的，且彼此独立 | 无 |
| **第 2 批（可验证）** | D3 静态断言 · Q4 真源比对 · O3 结构化日志 · B4 重试预算 · Q6 失败码回写 | 让第 1 批的成果**不会悄悄退化** | 第 1 批 |

## 七、执行步骤划分（S1–S8）

> **划分原则**：风险由小到大 —— 只读 → 纯 Python → 画布 → 无人值守 → 业务决策 → 产品化。
> **每步独立验收、独立回滚**；任一步停下，项目仍是可用状态，不会卡在半成品。

| 步骤 | 名称 | 包含条目 | 改动面 | 验收标准 | 需你决定 |
|---|---|---|---|---|---|
| **S1** ✅ | 观测基线 | D1 · Q4 | 只读 | `blocks.json` 可导出可 diff；画布/转录/文档三处块数自动比对一致 | — |
| **S2** ✅ | 输入止血 | Q1 · Q3 | 纯 Python | 当前 5 行不误伤；新增 6 类 fail + 2 类 warn，29 条用例全绿 | — |
| **S3** ✅ | 运维护栏 | O1 · O2 · O4 | 纯 Python | WPS 占锁可识别；P001 重复可查出；「上架中」可生成核对清单 | — |
| **S4** | 画布闸门 | D3 · Q6（D2 已提前完成） | 画布 + Python | 故意植入一个错误，三关能拦下；失败码回流 O 列 | 是否允许自动重跑 |
| **S5** | 运行可观测 | O3 · O5 | 画布 + Python | 一次运行产出 JSONL；异常能送达通知 | 告警渠道 |
| **S6** | 无人值守 | O6 · O7 · B4 | 画布 + 系统 | 连续 3 轮无残留进程；失败按预算自动重试 | 调度时段 |
| **S7** | 业务决策 | B1 · B2 · B3 · B5 | Python + 数据 | 能回答「这批货卖得动吗」 | 数据来源与口径 |
| **S8** | 产品化 | D5 · 工具链外提 | 仓库结构 | 独立 MCP server 可被第三方使用 | 是否开源 |

### 各步要点

**S1 · 观测基线** ✅（2026-11-07 完成）：先能看见，才谈得上改进。导出画布结构化快照入 git，写一个三处块数比对脚本。**只读，零风险**，但它是后面每一步「改完没改坏」的对照基准。

> 交付：`tools/canvas_snapshot.py`（`--check` 比对 / `--commit` 提交）、`tools/check_truth_source.py`（画布/转录/快照/文档四路比对，`--offline` 可脱机跑）、`project/canvas/<flow>.json`。
> **首次运行即抓到 2 处真实漂移**：AGENTS.md 第 37/62 行仍写 176 块（画布实际 185）——正是当天手工改块数时漏掉的。已修正，复跑全绿。

**S2 · 输入止血** ✅（2026-11-07 完成）：原计划做「分类段序校验」，中途**撤回**——见下方教训。最终交付的是分级校验。

> **为什么撤掉段序校验**：最初的设想是「成色词不该出现在非成色位置」，但当天日志证伪 —— P001 的 `发饰/DIY/全新/抓夹` 里，`全新` 就是一个**正常的三级分类节点**。同一个词既是分类节点又是字段值，靠词性无法区分。**分类顺序对不对，离线预检判断不了**，只有页面知道每级候选值；段序错已由画布侧两道守卫安全降级为「判失败跳过」，不再死循环。
>
> 交付：`precheck.py` 引入 **fail / warn 两级**（`fail` 语义不变，画布 `IF 预检["fail"]>0` 无需改动）。
> - **fail**：`CAT_FULLWIDTH`（全角斜杠拆不开）· `PRICE_ORDER`（原价<现价）· `PRICE_ORIG_BAD` · `IMG_BAD`（套图目录含非图片，画布是 `*.*` 全量上传）· `DESC_CONTACT`（真实手机号/微信号/QQ 号）
> - **warn**：`PRICE_EXTREME`（>10 万）· `CAT_DEPTH`（与同根品类历史上「上架成功」行的层数不一致，**自学习**，无样本则不判）
> - 29 条回归用例（`python -m unittest discover -s project/tools/tests`），含两条实测反例：「儿童**电话**手表」不得误判为留联系方式、全角斜杠必须拦下
> - 真实数据零误伤：5 行 `pass=5 warn=0 fail=0`

**S3 · 运维护栏** ✅（2026-11-07 完成）：`preflight.py`（锁文件/进程/凭据/表头/残留「上架中」）+ 已发布台账 + 查重 + 日志结构化 + 两阶段对账。这一天三件人工救火（关 WPS、对账、下架重复）全部代码化。

> **交付**：`preflight.py`（7 项只读检查，BLOCK 即拒绝启动）· `ledger.py`（`inflight → confirmed/failed/unknown/released` 状态机，查重只认 confirmed）· `reconcile.py`（列核对清单 + 按人裁决回填）· `log_parse.py`（两种导出格式 → JSONL + 每件耗时）· `verify.py`（D2 收口，一条命令跑完三项一致性检查）
> **红线**：脚本永不自动判定结果、「上架中」永不自动改回「待上架」——那是重发开关。
> **未完成**：O2b（画布加 `publish_begin` 日志）依赖 S4 跑一次验证。

**S4 · 画布闸门**：**从这里开始碰画布**。三关（编译 → 静态断言 → 转录 diff）+ 失败码回写 O 列。改完必须重跑转录，文档同源。

**S5 · 运行可观测**：自由文本日志改 JSONL，加失败/登录失效/超时告警。有了结构化数据，S6 的重试预算和 S7 的决策才有依据。

**S6 · 无人值守**：节流、资源回收、重试预算、调度。这一步之后才算「可托管」，而不是「能演示」。

**S7 · 业务决策**：唯一依赖**真实销售数据**的一步。前半段（入队/定价/择时）可以用规则起步，后半段（效果闭环）必须等数据长出来。

**S8 · 产品化**：把 `project/tools/shadowbot-canvas/` 抽成独立 MCP server，让别人也能用 Agent 驱动影刀；ADR 归档；案例材料成型。
